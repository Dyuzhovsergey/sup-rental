# Модель доступа и аудита SUP Rental

## Назначение документа

Этот документ является источником истины для аутентификации, авторизации,
пользовательских сессий и audit log SUP Rental.

Функциональные обязанности ролей описаны в
[`product-requirements.md`](product-requirements.md). Порядок реализации
определяет [`development-plan.md`](development-plan.md).

Модель реализуется поэтапно. Пользователи, Argon2id, server-side sessions,
login/logout, throttling, auth audit, защита бизнес-маршрутов, серверная
проверка ролей, управление операторами, audit изменений оборудования и
транзакционный audit создания и редактирования клиентов уже добавлены. Текущая
сборка остаётся локальной development-версией до отдельного инкремента HTTPS и
LAN-доступа.

## Модель эксплуатации

Первая версия работает на одном компьютере и принимает пользовательские
подключения только через loopback-интерфейс. Публикация приложения в локальную
сеть или интернет не входит в первоначальную модель угроз.

Переход к LAN-доступу требует отдельного инкремента с HTTPS, настройкой trusted
proxy, проверкой forwarded headers и обязательным `Secure` для session cookie.

Публичным техническим endpoint остаётся только `GET /health`. Он не раскрывает
конфигурацию, состояние базы данных или пользовательские сведения.

## Роли и матрица прав

В системе существуют роли `admin` и `operator`.

| Действие | `admin` | `operator` |
| --- | --- | --- |
| Управление учётными записями операторов | Да | Нет |
| Просмотр audit log | Да | Нет |
| Создание и редактирование оборудования | Да | Нет |
| Изменение состояния, списание и удаление оборудования | Да | Нет |
| Просмотр оборудования | Да | Да |
| Подбор оборудования для аренды | Просмотр | Да |
| Просмотр клиентов и аренд | Да | Да |
| Создание и изменение клиента | Нет по умолчанию | Да |
| Создание, выдача, возврат и завершение аренды | Нет по умолчанию | Да |
| Изменение завершённой аренды | Только отдельный audited-сценарий | Нет |

Проверка выполняется сервером для каждого защищённого действия после загрузки
актуальной учётной записи. Скрытие ссылки, кнопки или поля в HTML используется
только для понятности интерфейса и не является проверкой доступа.

## Единственный администратор

В системе существует ровно одна учётная запись `admin`. Неизменяемыми являются
её login, роль и активное состояние; password можно безопасно заменить.

Первый администратор создаётся одноразовой CLI-командой, которая использует тот
же application service и password hasher, что и приложение. Password вводится
без отображения в терминале и не передаётся аргументом команды, переменной
окружения или seed-миграцией.

Учётную запись администратора нельзя:

* создать через HTML-интерфейс;
* отключить;
* удалить;
* преобразовать в `operator`.

Если потребуется восстановить доступ администратора, используется отдельная
CLI-операция замены password с теми же правилами хранения и аудита.

Обе CLI-команды требуют интерактивный terminal и двукратный ввод password без
отображения символов. Password не принимается аргументом, через environment или
redirected stdin. Успешные действия сохраняют `admin.created` или
`admin.password_changed` в одной транзакции с изменением пользователя.

CLI выполняется до пользовательской аутентификации, поэтому у такого audit
event отсутствует actor. Target содержит ID и login администратора, а details —
только безопасный признак `source=admin_cli`.

## Жизненный цикл оператора

Администратор создаёт только учётные записи `operator` и сразу задаёт постоянные
login и password.

Временных паролей, `must_change_password` и обязательной смены при первом входе
нет. Оператор не имеет самостоятельной операции смены password.

Login:

* удаляет внешние пробелы;
* приводится к нижнему регистру и сравнивается без учёта регистра;
* после нормализации остаётся уникальным;
* содержит от 3 до 32 ASCII-символов;
* начинается с латинской буквы или цифры;
* после первого символа допускает латинские буквы, цифры, `.`, `_` и `-`;
* не меняется молча без отдельного бизнес-решения.

Password содержит от 6 до 128 Unicode-символов. Пробелы разрешены и считаются
частью password; приложение не удаляет их и не выполняет Unicode-нормализацию.
Требований к обязательному сочетанию регистра, цифр и специальных символов нет.
Минимум 6 символов выбран для удобства локальной работы операторов и является
осознанно более мягким правилом, чем современная рекомендация для систем без
MFA. Argon2id замедляет перебор, но не превращает простой короткий password в
стойкий, поэтому предсказуемые значения по-прежнему не рекомендуются.

Password является write-only значением. После создания невозможно получить ни
его открытое значение, ни password hash. При замене администратор задаёт новый
постоянный password, а все действующие сессии оператора отзываются.

Оператор не удаляется физически. Учётную запись можно отключить и повторно
активировать:

* отключение немедленно запрещает вход и отзывает все сессии;
* повторная активация не восстанавливает старые сессии;
* существующий password сохраняется, если администратор отдельно его не заменил;
* связи с арендой и audit log сохраняются.

Дата последнего успешного входа обновляется только после успешной
аутентификации. В PostgreSQL сохраняется абсолютный момент времени в
`timestamptz`, а административный интерфейс отображает его в московском часовом
поясе (UTC+3) без отдельной метки часового пояса.

## Хранение паролей

Пароли хешируются `golang.org/x/crypto/argon2` в режиме Argon2id с уникальной
16-байтовой криптографически случайной солью. Для первой версии используются
параметры `m=19456` KiB, `t=2`, `p=1` и производный ключ длиной 32 байта.
Hash хранится в версионированном формате вместе с алгоритмом, солью и
параметрами, чтобы будущее усиление параметров не требовало немедленной смены
всех паролей. При проверке производный ключ сравнивается за постоянное время.

Не допускаются:

* открытые пароли в PostgreSQL, `.env`, migration seed или application logs;
* быстрые общие hash-функции наподобие SHA-256 для хранения password;
* обратимое шифрование password;
* вывод password hash в HTML или audit log.

## Хранение пользователей

Учётные записи хранятся в таблице `users`. Минимальный состав данных:

* внутренний ID;
* нормализованный уникальный login;
* password hash;
* роль `admin` или `operator`;
* признак активности;
* nullable время последнего успешного входа.

PostgreSQL дополнительно проверяет формат нормализованного login, допустимые
роли, непустой password hash, активное состояние `admin` и существование не
более одной строки с ролью `admin`. Наличие хотя бы одного администратора
обеспечивает отдельная CLI-команда, а не migration seed.

Password hash не является полем безопасной доменной модели `User`. Repository
возвращает его отдельно только сценарию аутентификации и никогда не передаёт в
HTML, application log или audit log. Физическая операция удаления пользователя
в repository отсутствует.

CLI-reset изменяет password hash, отзывает все действующие сессии admin и
записывает audit event одной PostgreSQL-транзакцией.

## Вход и маршрутизация

После реализации доступа пользовательские маршруты закрыты по умолчанию.
Публичными остаются:

* `GET /login`;
* `POST /login`;
* `GET /health`;
* необходимые встроенные статические файлы.

`POST /logout` требует действующую сессию и CSRF-защиту.

Неавторизованный запрос к пользовательской странице перенаправляется на
`/login`. После успешного входа:

* `admin` переходит на панель администрирования;
* `operator` переходит на рабочее место оператора.

До появления клиентов и аренд рабочее место `operator` содержит переход к
read-only списку оборудования. Оператор может просматривать список и карточку,
но административные формы скрыты, а прямой запрос к изменяющему маршруту
отклоняется сервером с `403 Forbidden`.

Корневой `/` выполняет такое же role-aware перенаправление. Пользовательская
страница технического состояния приложения не создаётся.

Параметр возврата после login, если он будет добавлен, принимает только
проверенный внутренний путь и не допускает open redirect.

## Ошибки входа и блокировка

Для отсутствующей учётной записи, неправильного password и отключённого
оператора показывается одинаковое сообщение:

```text
Неверный логин или пароль.
```

Ответ не должен различаться по тексту, HTTP status или заметному времени так,
чтобы можно было определить существование login. Для отсутствующего
пользователя выполняется проверка заранее подготовленного dummy hash.

Действуют два независимых ограничения:

* не более 5 неуспешных попыток для нормализованного login за 15 минут;
* не более 20 неуспешных попыток с одного IP за 15 минут.

После превышения соответствующий ключ блокируется на 15 минут, а сервер
возвращает `429 Too Many Requests` с общим сообщением без указания сработавшего
лимита. Успешный вход очищает счётчик login.

Счётчики хранятся в PostgreSQL по SHA-256 digest нормализованного login и IP,
поэтому не сбрасываются при перезапуске server process.

По умолчанию IP определяется только из `RemoteAddr`, а proxy-заголовки
игнорируются. Это безопасный режим для локального запуска и прямого подключения.

При явно включённом `TRUST_PROXY_HEADERS=true` приложение считается запущенным
за заранее доверенным reverse proxy. В этом режиме IP клиента берётся из первого
адреса `X-Forwarded-For`, значение очищается от пробелов и проверяется как IP.
Отсутствующий или некорректный `X-Forwarded-For` приводит к отклонению login-запроса,
а не к fallback на другой источник.

Режим `TRUST_PROXY_HEADERS=true` предназначен для demo deployment за Render proxy.
Не следует включать его при прямом доступе клиента к приложению: клиент способен
самостоятельно подделать `X-Forwarded-For`. Другим proxy-заголовкам приложение не
доверяет без отдельного решения.

## Пользовательские сессии

Сессии хранятся на сервере в PostgreSQL. Browser получает только непрозрачный
криптографически случайный token, а в PostgreSQL сохраняется его digest.

Политика сессии:

* idle timeout — 8 часов;
* абсолютный срок — 24 часа;
* «Запомнить меня» отсутствует;
* login всегда создаёт новый token;
* logout отзывает текущую сессию;
* замена password и отключение пользователя отзывают все его сессии;
* истёкшая или отозванная сессия не восстанавливается.

Session cookie:

* `Path=/`;
* `HttpOnly`;
* `SameSite=Strict`;
* без `Domain`;
* с `Secure` при HTTPS.

Отключать `Secure` разрешено только явной конфигурацией loopback HTTP-режима.
Перед любым non-loopback deployment требуется HTTPS.

Cookie остаётся browser-session cookie без `Max-Age`, поэтому закрытие browser
завершает его локальное хранение. Серверные idle timeout и абсолютный срок
действуют независимо от наличия cookie.

Login и защищённые HTML-ответы получают `Cache-Control: no-store`.

## CSRF

Все unsafe-методы (`POST`, `PUT`, `PATCH`, `DELETE`) проходят глобальную
проверку `http.CrossOriginProtection`.

После входа каждая изменяющая HTML-форма дополнительно передаёт
session-bound synchronizer token в скрытом поле. Сервер проверяет наличие и
совпадение token до вызова бизнес-сервиса.

CSRF token:

* уникален для сессии;
* создаётся через `crypto/rand`;
* не попадает в URL, logs и audit events;
* меняется вместе с сессией;
* сравнивается способом, не раскрывающим частичное совпадение.

`SameSite` cookie является дополнительной защитой, но не заменяет серверную
проверку.

До успешного login session-bound token ещё отсутствует. Поэтому `POST /login`
защищается `http.CrossOriginProtection`; дополнительный synchronizer token
обязателен для изменяющих форм после создания пользовательской сессии.

## Audit log

Критические события сохраняются в отдельной append-only таблице
`audit_events`. Диагностические записи `slog` не заменяют audit log.

Минимальные поля события:

* время;
* nullable actor user ID;
* snapshot login и роли;
* код действия;
* тип и nullable ID объекта;
* понятная snapshot-метка объекта;
* результат;
* ограниченные структурированные детали.

Аудируются:

* успешные и неуспешные login;
* logout и срабатывание throttling;
* создание, отключение и активация оператора;
* замена password;
* создание и изменение оборудования;
* изменение состояния, списание и удаление оборудования;
* создание и изменение клиента;
* подтверждение, выдача, возврат, завершение и отмена аренды;
* административное изменение завершённой аренды;
* отказ в выполнении критического действия при практической ценности события.

Успешная критическая mutation и её audit event записываются одной
PostgreSQL-транзакцией. Если обязательное событие сохранить не удалось,
бизнес-изменение откатывается.

Для массового создания оборудования используется `equipment.batch_created` с
типом, кодом модели, тарифом, количеством и диапазоном номеров партии. Для
отдельных предметов используются `equipment.status_changed`,
`equipment.retired` и `equipment.deleted`. Изменение хранит snapshots `before`
и `after`; удаление — `before`. Исполнителем этих действий является `admin`, так
как `operator` имеет только read-only доступ к инвентарю.

Создание клиента активным оператором сохраняется как `client.created` с типом
объекта `client`, ID и snapshot ФИО. Телефон и полное содержимое формы в audit
event не записываются. Клиент и обязательное событие создаются одной
PostgreSQL-транзакцией.

Изменение контактных данных активным оператором сохраняется как
`client.updated`. Audit event содержит прежнее и новое ФИО и безопасный признак
изменения телефона, но не сам телефон. Обновление клиента и событие выполняются
одной PostgreSQL-транзакцией.

Создание подтверждённой аренды активным оператором сохраняется как
`rental.confirmed`. Event содержит ID клиента, плановый период и количество
физических единиц, но не телефон или полное содержимое формы. Блокировка
оборудования, создание аренды, snapshots состава и audit event выполняются
одной PostgreSQL-транзакцией.

Фактическая выдача активным оператором сохраняется как `rental.issued`. Event
содержит ID клиента, плановый период, фактическое время и количество единиц,
но не телефон. Переход аренды, изменение физического состояния всех единиц и
audit event выполняются одной PostgreSQL-транзакцией.

Отмена подтверждённой аренды активным оператором сохраняется как
`rental.cancelled`. Event содержит ID клиента, плановый период и количество
единиц, но не телефон. Переход `confirmed → cancelled` и audit event
выполняются одной PostgreSQL-транзакцией. Аренда и снимки её состава не
удаляются, чтобы сохранялась история действий.

Массовая выдача и отмена сохраняют отдельное существующее audit event для
каждой аренды. Вся выбранная группа и все её события записываются одной
PostgreSQL-транзакцией; ошибка любого события откатывает все изменения группы.

При удалении оборудования audit event хранит snapshot типа и инвентарного
номера без внешнего ключа на удаляемый предмет.

У неуспешного login и throttling event actor user ID и target ID могут
отсутствовать. Безопасной меткой служит нормализованный login, но в details не
попадают password, полное содержимое формы или session data.

В audit log запрещено записывать:

* password и password hash;
* session ID, session token и их digest;
* CSRF token;
* connection string;
* содержимое cookie;
* полные формы с персональными или секретными данными.

Audit events не удаляются и не изменяются через пользовательский интерфейс.

Страница `/admin/audit` доступна только активному `admin` и предоставляет
read-only выборку от новых событий к старым. Поддерживаются фильтры по
категории, результату, исполнителю, объекту и календарному периоду. Время
показывается по Москве, а в UI выводятся только явно распознанные безопасные
поля `details`; неизвестное содержимое JSON не отображается.

## Обязательные проверки будущей реализации

Автоматические тесты должны защищать:

* одинаковое поведение для неизвестного, отключённого и неверно
  аутентифицированного пользователя;
* Argon2id hash и проверку password без хранения открытого значения;
* создание, истечение, отзыв и rotation сессии;
* cookie attributes;
* CSRF-защиту каждого изменяющего маршрута;
* login throttling по login и IP;
* server-side запрет действий другой роли;
* немедленный отзыв сессий после смены password и отключения;
* отсутствие секретов в ответах и logs;
* атомарность бизнес-изменения и audit event;
* защиту от двойного выполнения конкурентных операций, где она требуется.
