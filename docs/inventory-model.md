# Модель инвентаря

## Назначение документа

Документ фиксирует подтверждённые бизнес-правила оборудования SUP Rental.
Роли и аренда описаны в [`product-requirements.md`](product-requirements.md),
а права и audit log — в [`access-model.md`](access-model.md).

## Модели и физические единицы

Данные разделены на каталог моделей и отдельные физические единицы:

```text
equipment_models — тип, код модели, часовой тариф и следующий номер
equipment        — физическая единица, состояние, модель и номер в модели
```

Каждая SUP-доска, весло и спасательный жилет остаются отдельными физическими
предметами с собственными внутренним ID, инвентарным номером и состоянием.
Отдельные таблицы для каждого типа не создаются.

Модель хранит:

| Поле | Назначение |
|---|---|
| `ID int64` | Внутренний идентификатор модели |
| `Kind Kind` | Тип оборудования |
| `ModelCode string` | Нормализованный латинский код модели |
| `HourlyRateKopecks int64` | Общий часовой тариф в копейках |
| `NextSequence int64` | Следующий порядковый номер физической единицы |

Физическая единица хранит:

| Поле | Назначение |
|---|---|
| `ID int64` | Неизменяемый внутренний идентификатор для связей |
| `ModelID int64` | Ссылка на модель |
| `SequenceNumber int64` | Порядковый номер внутри модели |
| `Status Status` | Текущее физическое состояние |

Для будущего подбора оборудования подтверждено необязательное поле `Note` —
примечание, важное при выдаче. Производитель, размер и другие специфические
характеристики пока не согласованы.

## Типы оборудования

| Значение | Отображение | Префикс номера |
|---|---|---|
| `sup_board` | SUP-доска | `SUP` |
| `paddle` | Весло | `PADDLE` |
| `life_jacket` | Спасательный жилет | `VEST` |

В Go `Kind` является отдельным строковым типом. PostgreSQL хранит `text` с
`CHECK`, а не enum, чтобы новые значения добавлялись последующей миграцией.

## Код модели и инвентарный номер

Код модели:

* обязателен;
* приводится к верхнему регистру;
* содержит только латинские буквы, цифры и дефисы;
* заменяет пробелы и `_` на дефис;
* объединяет повторные и удаляет крайние дефисы.

Например, ` carbon__pro 12 ` нормализуется в `CARBON-PRO-12`.

Инвентарный номер не вводится вручную и вычисляется в формате:

```text
PREFIX-MODEL-SEQUENCE
```

Например, третье весло модели `CARBON` получает `PADDLE-CARBON-3`. Пара
`model_id + sequence_number` уникальна. Удалённые номера не переиспользуются.
Связи с будущими арендами используют внутренний ID, а не номер.

## Тариф и массовое создание

Администратор вводит положительное целое число рублей за час. Приложение
преобразует его в копейки и не использует `float`: `500` рублей сохраняются как
`50000` копеек. Это позволяет будущему расчёту получасовых интервалов оставаться
точным.

Одна модель имеет один общий тариф. Повторное добавление той же пары
`kind + model_code`:

* с тем же тарифом создаёт дополнительные единицы и продолжает нумерацию;
* с другим тарифом возвращает конфликт и не меняет существующую модель.

Одна партия содержит от 1 до 100 единиц. Выделение диапазона, создание модели
при необходимости, вставка всех предметов и одно событие
`equipment.batch_created` выполняются одной PostgreSQL-транзакцией. Ошибка
audit event откатывает всю партию и изменение счётчика.

## Состояния

| Значение | Отображение | Назначение |
|---|---|---|
| `available` | Доступен | Предмет можно использовать |
| `issued` | Выдан | Предмет находится у клиента |
| `maintenance` | На обслуживании | Предмет временно нельзя выдавать |
| `retired` | Списан | Предмет выведен из эксплуатации |

Новая единица получает `available`. До появления аренды вручную разрешены:

```text
available   → maintenance, retired
maintenance → available, retired
```

`issued` изменяется будущими сценариями выдачи и возврата. `retired` является
конечным состоянием. Списание требует отдельного подтверждения. Списанный
предмет можно удалить только отдельным подтверждённым действием; после
появления аренды связь с историей должна запрещать физическое удаление.

## Редактирование

Форма редактирования разделяет три операции: изменение состояния, перенос
физической единицы в другую модель и изменение общего тарифа модели.

Перенос разрешён только для `available` и `maintenance`. Целевая пара
`kind + model_code` может быть существующей или новой. Для существующей модели
введённый тариф должен совпадать с её текущим тарифом; новая модель создаётся с
указанным тарифом. Единица получает следующий номер целевой модели, но сохраняет
внутренний ID и состояние. Старый и новый номера записываются в
`equipment.model_changed` одной транзакцией с переносом.

Общий тариф изменяется отдельной операцией и применяется ко всем физическим
единицам модели. Интерфейс явно предупреждает о массовом влиянии. Событие
`equipment.model_rate_changed` сохраняет старый и новый тариф и количество
затронутых единиц одной транзакцией с изменением.

`issued` и `retired` нельзя переносить между моделями или использовать как
точку входа для изменения тарифа. Инвентарный номер вручную не редактируется.

## Роли и доступ

* `admin` создаёт партии, меняет состояние, списывает и удаляет оборудование;
* `operator` только просматривает оборудование и позднее выбирает его в аренду;
* права проверяются на сервере, скрытие элемента HTML не является авторизацией;
* критическое изменение и audit event записываются одной транзакцией.

## Доступность для аренды

Техническое состояние и доступность на период — разные понятия. Предмет
доступен на весь выбранный полуоткрытый интервал, только если состояние
допускает выдачу и интервал не пересекается с подтверждённой или активной
арендой. Сервер повторно проверяет доступность при подтверждении, а механизм
конкурентности PostgreSQL не должен допускать двойной выдачи.

Доменная модель аренды использует статусы `draft`, `confirmed`, `active`,
`completed` и `cancelled`, а планируемое время разбивается на получасовые слоты
полуоткрытого интервала `[start, end)`. Поэтому аренды, границы которых только
соприкасаются, не конфликтуют. Транзакционная защита от двойной выдачи и
правила окончательной стоимости согласуются отдельными инкрементами аренды.

Состав аренды уже моделируется отдельными физическими единицами, а не только
количеством моделей. Для каждой позиции сохраняется снимок инвентарного номера,
типа, модели и часового тарифа. Поэтому последующее изменение модели или тарифа
не переписывает историю подтверждённой аренды. Предварительная стоимость
черновика рассчитывается по снимкам в копейках и числу получасовых слотов. При
будущем подтверждении снимки должны быть заменены актуальными данными в той же
транзакции, которая проверяет доступность.
