# Первоначальная модель инвентаря

## Назначение документа

Документ фиксирует бизнес-решения, необходимые для первого вертикального среза
учёта оборудования.

Модель является минимальной: она описывает общие свойства физических предметов,
но не придумывает неподтверждённые характеристики досок, вёсел и жилетов.

## Общая сущность

SUP-доски, вёсла и спасательные жилеты представлены одной сущностью
`equipment.Item`.

Все эти предметы:

* являются отдельными физическими единицами инвентаря;
* имеют собственный уникальный инвентарный номер;
* относятся к одному из известных типов;
* имеют текущее физическое состояние.

Отдельные сущности и таблицы для каждого типа пока не создаются. Если позднее
появятся подтверждённые специфические характеристики, они будут добавлены
отдельным инкрементом и миграцией.

## Поля

Первоначальная модель содержит:

| Поле | Назначение |
|---|---|
| `ID int64` | Внутренний технический идентификатор для связей |
| `InventoryNumber string` | Понятный администратору инвентарный номер |
| `Kind Kind` | Тип физического предмета |
| `Status Status` | Текущее физическое состояние |

В PostgreSQL для `ID` предварительно выбран `bigint generated as identity`.
Инвентарный номер не используется как primary key, потому что ошибочно
введённый бизнес-номер в будущем может потребовать исправления.

Название, модель, производитель, размер, стоимость, комментарий и временные
метки в первый срез не входят: требования к ним пока не подтверждены.

## Типы оборудования

Первоначально определены значения `Kind`:

| Значение | Отображение |
|---|---|
| `sup_board` | SUP-доска |
| `paddle` | Весло |
| `life_jacket` | Спасательный жилет |

В доменной модели `Kind` будет отдельным строковым типом Go. В PostgreSQL
значения будут храниться как `text` с ограничением `CHECK`, а не как
PostgreSQL enum. Это позволит добавлять новые типы обычной последующей
миграцией.

## Инвентарный номер

Действуют следующие правила:

* номер обязателен;
* пробелы в начале и конце удаляются;
* после удаления пробелов номер не должен быть пустым;
* исходный регистр сохраняется для отображения;
* уникальность проверяется без учёта регистра.

Например, `SUP-001`, `sup-001` и ` Sup-001 ` считаются одним номером.

Ограничение должно проверяться сервисом приложения и PostgreSQL. Для защиты от
конкурентного создания одинаковых номеров в PostgreSQL будет использоваться
уникальный индекс по `lower(inventory_number)`.

Формат номера пока не ограничивается регулярным выражением.

## Состояния

Определены значения `Status`:

| Значение | Отображение | Назначение |
|---|---|---|
| `available` | Доступен | Предмет можно использовать |
| `issued` | Выдан | Предмет находится у клиента |
| `maintenance` | На обслуживании | Предмет временно нельзя выдавать |
| `retired` | Списан | Предмет выведен из эксплуатации |

Отдельный статус «ремонт» не вводится. `maintenance` покрывает временное
обслуживание и ремонт до появления требования различать эти процессы.

Новый предмет автоматически получает `available`.

### Допустимые переходы

Предварительно разрешены переходы:

| Из | В |
|---|---|
| `available` | `issued` |
| `issued` | `available` |
| `available` | `maintenance` |
| `issued` | `maintenance` |
| `maintenance` | `available` |
| `available` | `retired` |
| `maintenance` | `retired` |

`retired` является конечным состоянием. Автоматическое или обычное
восстановление списанного предмета не предусматривается. Если такая
необходимость появится, она потребует отдельного бизнес-решения.

Переходы фиксируются для согласованности будущей модели, но изменение статуса
не входит в первый бизнес-срез.

## Бронирование

Бронирование будет отдельной будущей сущностью, а не значением `Status`.

У бронирования должны появиться собственные данные: клиент, период, состав
оборудования, отмена и история. Предмет может быть физически доступен сейчас,
но забронирован на будущий период, поэтому одно поле состояния не может
корректно выразить оба факта.

Будущая доступность будет определяться физическим состоянием вместе с активными
арендами и бронированиями на нужный период.

## Первый бизнес-срез

Первый срез этапа учёта оборудования — создание и просмотр списка оборудования.

Администратор сможет:

1. Открыть `GET /equipment`.
2. Увидеть список зарегистрированных предметов.
3. Ввести инвентарный номер.
4. Выбрать тип предмета.
5. Создать предмет через `POST /equipment`.
6. Увидеть новый предмет со статусом «Доступен».

После успешного создания используется Post/Redirect/Get:

```text
POST /equipment
        ↓
303 See Other
        ↓
GET /equipment
```

Срез должен пройти через все слои:

```text
доменная модель
    ↓
сервис Create/List
    ↓
PostgreSQL repository и миграция
    ↓
HTTP-обработчики
    ↓
HTML-форма и список
    ↓
unit-, HTTP- и integration-тесты
```

## Что не входит в первый срез

В первый срез не входят:

* редактирование предмета;
* изменение состояния;
* удаление, списание и восстановление;
* просмотр отдельной карточки;
* бронирование;
* аренда и возврат;
* клиенты;
* правила обязательного комплекта из доски, весла и жилета;
* специфические характеристики разных типов;
* цены;
* поиск, фильтрация и пагинация;
* импорт существующего инвентаря;
* история изменения оборудования.

Правила комплекта необходимо согласовать перед реализацией аренды, но они не
влияют на регистрацию отдельных физических предметов.
