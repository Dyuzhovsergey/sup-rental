# План разработки SUP Rental

## 1. Назначение проекта

SUP Rental — приложение для учёта оборудования, клиентов и почасовой аренды SUP-досок.

Проект создаётся одновременно для двух целей:

1. Практическое изучение Go.
2. Изучение настройки Codex для работы с репозиторием в VS Code.

Разработка ведётся небольшими, понятными и проверяемыми инкрементами.

## 2. Подтверждённые бизнес-требования

### Пользователь приложения

С программой работает один администратор.

Несколько ролей пользователей и разграничение прав пока не требуются.

Необходимость локальной авторизации будет рассмотрена позднее.

### Инвентарь

В программе должен учитываться следующий инвентарь:

* SUP-доски;
* вёсла;
* спасательные жилеты.

Каждый отдельный предмет имеет уникальный инвентарный номер.

Пока не определено, будет ли весь инвентарь представлен одной общей сущностью или несколькими отдельными сущностями.

### Состояния оборудования

Предварительно определены состояния:

* доступен;
* забронирован;
* выдан;
* списан.

Перед реализацией необходимо определить:

* какие переходы между состояниями разрешены;
* является ли бронирование состоянием оборудования или отдельной сущностью;
* можно ли вернуть списанное оборудование в эксплуатацию;
* требуется ли состояние «ремонт» или «обслуживание».

### Клиенты

Для клиента необходимо хранить:

* ФИО;
* номер телефона;
* историю аренд.

Перед реализацией необходимо определить:

* формат и проверку номера телефона;
* правила поиска дубликатов клиентов;
* возможность редактирования клиента;
* возможность архивирования клиента.

### Аренда

Подтверждены следующие правила:

* аренда почасовая;
* одна аренда может включать несколько SUP-досок;
* скидки отсутствуют;
* завершённые аренды должны сохраняться в истории.

Перед реализацией необходимо определить:

* правила расчёта стоимости;
* округление неполного часа;
* состав комплекта оборудования;
* правила выдачи вёсел и жилетов;
* наличие предварительного бронирования;
* правила отмены бронирования;
* фиксацию времени фактической выдачи;
* фиксацию времени возврата;
* правила просрочки;
* необходимость учёта оплаты;
* необходимость залога;
* правила обработки повреждений.

### История действий

Не требуется хранить:

* историю изменения каждой записи;
* имя сотрудника, выполнившего изменение.

История аренд при этом должна сохраняться.

### Установка и доступ

Доступ через интернет не требуется.

Предполагается локальная установка приложения с использованием Docker Compose.

Перед подготовкой production-установки необходимо определить:

* работа на одном компьютере или в локальной сети;
* способ резервного копирования PostgreSQL;
* способ восстановления данных;
* порядок обновления приложения;
* срок хранения журналов приложения.

## 3. Архитектурное направление

Проект разрабатывается как модульный монолит.

Предпочтительное направление зависимостей:

```text
HTTP-обработчики
        ↓
сервисы приложения
        ↓
интерфейсы репозиториев
        ↓
PostgreSQL-репозитории
        ↓
PostgreSQL
```

Основные ограничения:

* HTTP-обработчики не выполняют SQL-запросы;
* PostgreSQL-репозитории не содержат HTTP-логику;
* бизнес-логика не зависит от HTTP, PostgreSQL и Docker;
* зависимости создаются явно в точке входа;
* dependency injection выполняется вручную через конструкторы;
* интерфейсы создаются только при наличии реальной необходимости;
* конфигурация передаётся через переменные окружения;
* секреты не хранятся в Git;
* ошибки оборачиваются с понятным контекстом;
* операции ввода-вывода получают `context.Context`;
* приложение должно поддерживать graceful shutdown.

## 4. Этапы разработки

Проект развивается небольшими вертикальными срезами.

Вертикальный срез означает, что одна пользовательская функция по возможности реализуется полностью:

```text
доменная модель
    ↓
сервис приложения
    ↓
репозиторий и PostgreSQL
    ↓
HTTP-обработчики
    ↓
HTML-интерфейс
    ↓
автоматические тесты
```

Такой подход позволяет после каждого бизнес-инкремента получать функцию, которую можно проверить через браузер, а не откладывать весь frontend до завершения backend.

### Этап 1. Подготовка репозитория и Codex

Цель этапа — подготовить безопасную и понятную среду разработки.

В рамках этапа необходимо:

* заполнить `README.md`;
* создать глобальный план разработки;
* создать и проверить корневой `AGENTS.md`;
* настроить русский язык общения с Codex;
* создать минимальный `.codex/config.toml`;
* создать безопасный `.codex/rules/default.rules`;
* создать instruction-only skill `verify-sup-rental`;
* проверить, что Codex видит инструкции, конфигурацию, rules и skill.

На этом этапе не создаются бизнес-сущности, PostgreSQL-схема приложения и frontend.

### Этап 2. Технический вертикальный срез

Цель этапа — создать минимальное, полностью запускаемое приложение без бизнес-функций.

Перед созданием первой HTML-страницы необходимо кратко сравнить и согласовать первоначальный frontend-подход.

Предварительно рекомендуется использовать:

* серверный рендеринг через Go `html/template`;
* обычный HTML;
* простой CSS;
* минимальное количество JavaScript.

В рамках технического среза необходимо:

* создать точку входа приложения;
* добавить загрузку конфигурации через переменные окружения;
* добавить структурированное логирование;
* запустить HTTP-сервер;
* добавить health endpoint;
* реализовать graceful shutdown;
* подключить PostgreSQL;
* создать первую техническую миграцию;
* добавить простую HTML-страницу состояния приложения;
* добавить первые unit- и HTTP-тесты;
* создать Dockerfile;
* создать Docker Compose с приложением и PostgreSQL;
* описать локальный запуск.

Результатом должен стать проект, который можно получить из Git, собрать и запустить одной понятной последовательностью команд.

### Этап 3. Уточнение модели первой версии

Цель этапа — согласовать правила, необходимые для первой бизнес-функции.

До создания таблиц оборудования необходимо определить:

* будет ли весь инвентарь общей сущностью или отдельными сущностями;
* какие характеристики хранятся для доски, весла и жилета;
* какие состояния оборудования существуют;
* какие переходы между состояниями разрешены;
* является ли бронирование состоянием оборудования или отдельной сущностью;
* требуется ли состояние «обслуживание» или «ремонт»;
* можно ли восстановить списанное оборудование;
* входят ли весло и жилет в обязательный комплект с доской;
* какой минимальный функционал должен войти в первую версию.

Этот этап не должен блокировать техническую подготовку приложения, но должен завершиться до реализации бизнес-таблиц и бизнес-правил.

### Этап 4. Учёт оборудования

Цель этапа — реализовать первый законченный бизнес-сценарий.

Этап выполняется вертикальными инкрементами и включает:

* доменную модель оборудования;
* миграции PostgreSQL;
* PostgreSQL-репозиторий;
* сервис приложения;
* HTTP-обработчики;
* HTML-страницу списка оборудования;
* HTML-форму создания оборудования;
* просмотр одной единицы оборудования;
* редактирование;
* изменение состояния;
* списание или архивирование;
* unit-тесты бизнес-правил;
* HTTP-тесты;
* integration-тесты репозитория.

Необязательно реализовывать все операции одним инкрементом. Например, создание и список оборудования могут быть первым рабочим срезом, а редактирование и списание — следующими.

### Этап 5. Учёт клиентов

Цель этапа — добавить работу с клиентами.

Этап включает:

* доменную модель клиента;
* миграции PostgreSQL;
* создание клиента;
* поиск клиента;
* просмотр клиента;
* изменение контактных данных;
* HTML-страницу списка клиентов;
* HTML-формы создания и редактирования;
* подготовку отображения истории аренд;
* unit-, HTTP- и integration-тесты.

Окончательные правила проверки телефонных номеров и поиска дубликатов должны быть согласованы перед реализацией.

### Этап 6. Аренда и возврат

Цель этапа — реализовать основной рабочий процесс проката.

Перед реализацией необходимо определить правила расчёта стоимости, выдачи комплекта и завершения аренды.

Этап включает:

* создание почасовой аренды;
* связь аренды с клиентом;
* добавление нескольких SUP-досок;
* добавление вёсел и жилетов;
* проверку доступности оборудования;
* фиксацию фактического времени выдачи;
* возврат оборудования;
* фиксацию фактического времени возврата;
* расчёт стоимости;
* сохранение завершённой аренды в истории;
* HTML-формы оформления выдачи и возврата;
* страницы активных и завершённых аренд;
* тестирование бизнес-правил;
* проверку конкурентного изменения доступности оборудования, если оно станет актуально.

### Этап 7. Дополнительные бизнес-функции

Состав этапа определяется после появления основной работающей версии.

Возможные функции:

* предварительное бронирование;
* отмена бронирования;
* учёт оплаты;
* просрочка;
* залог;
* фиксация повреждений;
* обслуживание;
* ремонт;
* списание оборудования;
* простые отчёты.

Каждая функция добавляется отдельным вертикальным инкрементом только после согласования требований.

### Этап 8. Улучшение пользовательского интерфейса

Базовые HTML-страницы создаются вместе с соответствующими бизнес-функциями на предыдущих этапах.

На этом этапе улучшается уже работающий интерфейс:

* общая навигация;
* таблицы;
* поиск;
* фильтры;
* сортировка;
* понятные сообщения об ошибках;
* отображение результатов операций;
* подтверждение опасных действий;
* базовая адаптация под ноутбук или планшет;
* улучшение CSS;
* минимальный JavaScript там, где он действительно нужен.

Перед добавлением HTMX необходимо отдельно сравнить его с обычными HTML-формами и согласовать использование.

Отдельное SPA-приложение на React, Vue или другом frontend-фреймворке не создаётся без практической необходимости и отдельного решения.

### Этап 9. Подготовка к установке у заказчика

Цель этапа — подготовить приложение к безопасной локальной эксплуатации.

Этап включает:

* production Dockerfile;
* Docker Compose;
* постоянный PostgreSQL volume;
* `.env.example`;
* выполнение миграций при установке и обновлении;
* healthcheck;
* резервное копирование PostgreSQL;
* восстановление из резервной копии;
* порядок обновления приложения;
* диагностику проблем;
* инструкцию для пользователя;
* политику хранения и ротации логов;
* проверку работы на одном компьютере или в локальной сети.

Разрушительные команды Docker и операции удаления данных не должны выполняться без явного подтверждения пользователя.

### Этап 10. Повышение качества

После появления достаточного количества рабочего кода необходимо рассмотреть:

* расширение unit-тестов;
* integration-тесты;
* тесты основных пользовательских сценариев;
* линтер;
* CI;
* аудит безопасности;
* улучшение логирования;
* метрики при наличии практической необходимости;
* документацию архитектурных решений;
* анализ производительности;
* проверку процедуры резервного копирования и восстановления.

Микросервисы, брокеры сообщений, Kubernetes и отдельный observability-стек не добавляются без практической необходимости.

## 5. Правила работы по инкрементам

Перед изменениями необходимо описать:

1. Цель изменения.
2. Причину изменения.
3. Создаваемые и изменяемые файлы.
4. Архитектурные решения.
5. Риски и альтернативы.

После изменений необходимо описать:

1. Что реализовано.
2. Как работает решение.
3. Какие понятия Go использованы.
4. Какие команды требуется выполнить.
5. Как провести ручную проверку.
6. Какие автоматические тесты должны пройти.
7. Какие ограничения остаются.
8. Какой следующий инкремент является логичным.
9. Какое сообщение Git-коммита рекомендуется.

Каждый диалог по проекту должен завершаться одним конкретным следующим шагом.

## 7. Критерии завершения текущего инкремента

Инкремент со skill считается завершённым, когда:

* создан `.agents/skills/verify-sup-rental/SKILL.md`;
* указаны корректные `name` и `description`;
* описание позволяет Codex понять, когда нужно выбрать skill;
* проверки выполняются в логически правильном порядке;
* неприменимые к текущему состоянию проекта команды корректно пропускаются;
* skill не содержит разрушительных действий;
* skill не выполняет `git commit` или `git push`;
* Codex может выбрать skill по прямому упоминанию;
* проверено автоматическое или явное применение skill;
* предложено понятное сообщение Git-коммита.
