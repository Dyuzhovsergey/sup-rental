# План разработки SUP Rental

## 1. Назначение проекта

SUP Rental — приложение для учёта оборудования, клиентов и почасовой аренды SUP-досок.

Проект создаётся одновременно для двух целей:

1. Практическое изучение Go.
2. Изучение настройки Codex для работы с репозиторием в VS Code.

Разработка ведётся небольшими, понятными и проверяемыми инкрементами.

## 2. Подтверждённые бизнес-требования

### Пользователь приложения

С программой работает один администратор.

Несколько ролей пользователей и разграничение прав пока не требуются.

Необходимость локальной авторизации будет рассмотрена позднее.

### Инвентарь

В программе должен учитываться следующий инвентарь:

* SUP-доски;
* вёсла;
* спасательные жилеты.

Каждый отдельный предмет имеет уникальный инвентарный номер.

Пока не определено, будет ли весь инвентарь представлен одной общей сущностью или несколькими отдельными сущностями.

### Состояния оборудования

Предварительно определены состояния:

* доступен;
* забронирован;
* выдан;
* списан.

Перед реализацией необходимо определить:

* какие переходы между состояниями разрешены;
* является ли бронирование состоянием оборудования или отдельной сущностью;
* можно ли вернуть списанное оборудование в эксплуатацию;
* требуется ли состояние «ремонт» или «обслуживание».

### Клиенты

Для клиента необходимо хранить:

* ФИО;
* номер телефона;
* историю аренд.

Перед реализацией необходимо определить:

* формат и проверку номера телефона;
* правила поиска дубликатов клиентов;
* возможность редактирования клиента;
* возможность архивирования клиента.

### Аренда

Подтверждены следующие правила:

* аренда почасовая;
* одна аренда может включать несколько SUP-досок;
* скидки отсутствуют;
* завершённые аренды должны сохраняться в истории.

Перед реализацией необходимо определить:

* правила расчёта стоимости;
* округление неполного часа;
* состав комплекта оборудования;
* правила выдачи вёсел и жилетов;
* наличие предварительного бронирования;
* правила отмены бронирования;
* фиксацию времени фактической выдачи;
* фиксацию времени возврата;
* правила просрочки;
* необходимость учёта оплаты;
* необходимость залога;
* правила обработки повреждений.

### История действий

Не требуется хранить:

* историю изменения каждой записи;
* имя сотрудника, выполнившего изменение.

История аренд при этом должна сохраняться.

### Установка и доступ

Доступ через интернет не требуется.

Предполагается локальная установка приложения с использованием Docker Compose.

Перед подготовкой production-установки необходимо определить:

* работа на одном компьютере или в локальной сети;
* способ резервного копирования PostgreSQL;
* способ восстановления данных;
* порядок обновления приложения;
* срок хранения журналов приложения.

## 3. Архитектурное направление

Проект разрабатывается как модульный монолит.

Предпочтительное направление зависимостей:

```text
HTTP-обработчики
        ↓
сервисы приложения
        ↓
интерфейсы репозиториев
        ↓
PostgreSQL-репозитории
        ↓
PostgreSQL
```

Основные ограничения:

* HTTP-обработчики не выполняют SQL-запросы;
* PostgreSQL-репозитории не содержат HTTP-логику;
* бизнес-логика не зависит от HTTP, PostgreSQL и Docker;
* зависимости создаются явно в точке входа;
* dependency injection выполняется вручную через конструкторы;
* интерфейсы создаются только при наличии реальной необходимости;
* конфигурация передаётся через переменные окружения;
* секреты не хранятся в Git;
* ошибки оборачиваются с понятным контекстом;
* операции ввода-вывода получают `context.Context`;
* приложение должно поддерживать graceful shutdown.

## 4. Этапы разработки

### Этап 1. Подготовка репозитория и Codex

* заполнить README;
* создать план разработки;
* создать `AGENTS.md`;
* проверить, что Codex читает `AGENTS.md`;
* создать минимальный `.codex/config.toml`;
* создать безопасные правила запуска команд;
* создать instruction-only skill проверки проекта.

### Этап 2. Технический вертикальный срез

* создать точку входа приложения;
* добавить загрузку конфигурации;
* добавить структурированное логирование;
* запустить HTTP-сервер;
* добавить health endpoint;
* реализовать graceful shutdown;
* подключить PostgreSQL;
* создать первую миграцию;
* добавить простую HTML-страницу;
* добавить Dockerfile;
* добавить Docker Compose;
* написать первые автоматические тесты;
* описать локальный запуск.

### Этап 3. Первая бизнес-функция

После дополнительного уточнения требований реализовать один небольшой законченный сценарий.

Предварительный кандидат — учёт инвентаря:

* создание единицы оборудования;
* просмотр списка;
* просмотр одной записи;
* редактирование;
* изменение состояния;
* архивирование или списание.

Окончательная модель оборудования должна быть согласована перед реализацией.

### Этап 4. Клиенты

* создание клиента;
* поиск клиента;
* просмотр клиента;
* изменение контактных данных;
* просмотр истории аренд.

### Этап 5. Аренда и возврат

* создание почасовой аренды;
* добавление нескольких SUP-досок;
* добавление связанного оборудования;
* проверка доступности;
* выдача;
* возврат;
* сохранение истории;
* проверка бизнес-правил автоматическими тестами.

### Этап 6. Пользовательский интерфейс

Перед реализацией необходимо сравнить:

* серверный HTML через `html/template`;
* серверный HTML с минимальным JavaScript;
* серверный HTML с HTMX;
* отдельное frontend-приложение.

Предварительно предпочтителен серверный HTML через Go, обычный CSS и минимальное количество JavaScript.

### Этап 7. Установка у заказчика

* production Dockerfile;
* Docker Compose;
* PostgreSQL volume;
* `.env.example`;
* миграции;
* healthcheck;
* резервное копирование;
* восстановление;
* обновление приложения;
* диагностика проблем;
* инструкция по эксплуатации.

### Этап 8. Повышение качества

После появления достаточного количества рабочего кода:

* расширить unit-тесты;
* добавить integration-тесты;
* добавить линтер;
* добавить CI;
* провести аудит безопасности;
* улучшить логирование;
* добавить необходимые метрики;
* оформить архитектурные решения.

Микросервисы, брокеры сообщений, Kubernetes и отдельный observability-стек не добавляются без практической необходимости.

## 5. Правила работы по инкрементам

Перед изменениями необходимо описать:

1. Цель изменения.
2. Причину изменения.
3. Создаваемые и изменяемые файлы.
4. Архитектурные решения.
5. Риски и альтернативы.

После изменений необходимо описать:

1. Что реализовано.
2. Как работает решение.
3. Какие понятия Go использованы.
4. Какие команды требуется выполнить.
5. Как провести ручную проверку.
6. Какие автоматические тесты должны пройти.
7. Какие ограничения остаются.
8. Какой следующий инкремент является логичным.
9. Какое сообщение Git-коммита рекомендуется.

Каждый диалог по проекту должен завершаться одним конкретным следующим шагом.

## 6. Текущий инкремент

Текущий инкремент включает только документацию и инструкции для Codex:

* заполнение `README.md`;
* создание `docs/development-plan.md`;
* создание `AGENTS.md`;
* проверку работы инструкций Codex.

В текущем инкременте не создаются:

* Go-пакеты приложения;
* HTTP-сервер;
* бизнес-сущности;
* миграции;
* PostgreSQL;
* Dockerfile;
* Docker Compose;
* frontend.

## 7. Критерии завершения текущего инкремента

Инкремент считается завершённым, когда:

* README содержит краткое описание проекта;
* подтверждённые требования отделены от открытых вопросов;
* этапы разработки записаны в документации;
* корневой `AGENTS.md` содержит правила работы с репозиторием;
* Codex подтверждает, что прочитал инструкции;
* Git не содержит случайных или временных файлов;
* изменения просмотрены перед коммитом;
* создано понятное сообщение коммита.
