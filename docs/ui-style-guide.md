# UI style guide SUP Rental

## Назначение документа

Этот документ является единственным источником истины для визуального языка
SUP Rental. Все новые страницы и изменения существующих страниц должны
соответствовать ему без повторного согласования общего стиля.

Отдельные особенности конкретной функции могут согласовываться самостоятельно,
но не должны создавать другую палитру, навигацию или систему компонентов.

## Направление

Выбран стиль **Modern SaaS Admin Dashboard**:

* спокойный и функциональный минимализм;
* Material-подобные surfaces, elevation, chips и buttons;
* понятная иерархия без декоративного шума;
* компактность для частого использования;
* sidebar на ноутбуке;
* умеренный Bento Grid только на главной панели;
* одинаковый shell и визуальный язык для интерфейсов обеих ролей.

Glassmorphism, крупная декоративная типографика, сложные градиенты и
анимационные библиотеки не являются частью выбранного направления.

## Техническая основа

Интерфейс остаётся серверным:

* Go `html/template`;
* семантический HTML;
* один общий встроенный CSS;
* системный шрифт;
* единый набор простых inline SVG-иконок;
* минимальный vanilla JavaScript, включая общий переключатель темы.

Не добавляются без отдельного решения:

* Tailwind и другие CSS-фреймворки;
* React, Vue и другие SPA-фреймворки;
* внешние шрифты;
* библиотеки компонентов и иконок;
* декоративные animation libraries.

CSS и шаблоны встраиваются в Go-бинарник через `go:embed`, поэтому выбранный
интерфейс входит в Docker image и не зависит от наличия Codex skill на целевом
компьютере.

## Темы и цветовые токены

Интерфейс поддерживает полноценные светлую и тёмную темы. Тёмная тема сохраняет
Modern SaaS Admin Dashboard и использует самостоятельную палитру с несколькими
уровнями поверхности, а не инверсию светлых цветов.

Компоненты используют семантические CSS custom properties. Hardcoded color
допустим только внутри таблицы token mappings, но не в правилах отдельных
компонентов.

Основные mappings:

поверхностей, а более контрастный `Control outline` — для границ полей и других
интерактивных элементов.

## Выбор и переключение темы

На защищённых страницах переключатель находится в общем sidebar рядом с
профилем пользователя. На странице входа он доступен отдельно без sidebar.
Переключатель является обычной `button`, имеет видимый текст, `aria-label`,
`aria-pressed`, SVG-иконку и область нажатия не меньше `44px`.

Явный выбор `light` или `dark` хранится только в браузере в `localStorage` и
имеет приоритет над системной настройкой. Пока выбора нет, используется
`prefers-color-scheme`. Тема устанавливается через `data-theme` на корневом
`html` до загрузки основного CSS, чтобы между server-rendered страницами не
возникала заметная вспышка неправильной темы. Недоступность `localStorage` не
ломает страницу: текущая тема продолжает работать без сохранения.

Все новые surfaces, controls, status chips, alerts, таблицы и состояния
interaction должны проверяться независимо в обеих темах. Для каждой темы
обязательны читаемые placeholder и disabled controls, различимые границы,
видимый focus и отсутствие передачи состояния только цветом.

## Типографика и размеры

Шрифт:

```css
font-family:
    ui-sans-serif,
    system-ui,
    -apple-system,
    BlinkMacSystemFont,
    "Segoe UI",
    sans-serif;
```

Базовые размеры:

* body — `16px`, line-height не меньше `1.5`;
* компактные данные и действия таблицы — `14px`;
* `h1` — `28px`, line-height `1.25`;
* заголовок панели — `18px`, line-height `1.35`;
* вторичный текст — `14px` с достаточным контрастом.

Используется шкала отступов `4, 8, 12, 16, 24, 32, 48px`.

Радиусы:

* компактные controls — `10px`;
* cards и panels — `16px`;
* chips и pill-buttons — `999px`.

Допускается один лёгкий уровень тени. Тень не заменяет видимую границу
поверхности.

## Layout

Целевой интерфейс проектируется desktop-first для:

* `1366×768`;
* `1440×900`.

Основной layout:

* sidebar шириной `232px`;
* main content с максимальной шириной `1216px`;
* desktop gutters `32px`;
* фиксированное расположение основной навигации;
* отсутствие горизонтальной прокрутки всей страницы.

Специальная адаптация под планшет и телефон пока не входит в критерии приёмки.
Это не разрешает:

* искусственный `min-width`, ломающий viewport;
* отключение browser zoom;
* потерю keyboard navigation;
* скрытие значимой информации без альтернативы;
* недоступные формы или действия.

Полноценная tablet/mobile-адаптация выполняется отдельным будущим
инкрементом.

## Общий shell и навигация

Все защищённые страницы используют общий shell:

* единый brand block;
* sidebar;
* активное состояние текущего раздела;
* область основного содержимого;
* действие logout;
* отображение текущего login и роли там, где это помогает ориентации.

Навигация администратора включает только доступные административные разделы.
Навигация оператора ориентирована на ежедневную аренду и не содержит управления
пользователями, audit log и lifecycle оборудования.

Login использует те же цвета, typography и components, но не показывает
sidebar до успешной аутентификации.

Техническое состояние приложения не отображается в sidebar или на dashboard.
`/health` остаётся отдельным машинным endpoint.

## Главные панели

Bento Grid используется умеренно и только для кратких показателей главной
панели. Он не должен превращать каждую форму или таблицу в набор плиток.

Панель администратора показывает только фактические бизнес-показатели.
Отсутствующие модели аренды или финансов не имитируются нулевыми декоративными
cards.

Рабочее место оператора отдаёт приоритет:

* действию «Создать аренду»;
* активным и просроченным арендам;
* времени планового возврата;
* поиску;
* предупреждениям о конфликте.

## Panels и cards

Forms, details и confirmations размещаются в общей `surface`/`panel`:

* белый фон;
* единая граница;
* согласованный radius;
* короткий header с названием и необязательным описанием;
* предсказуемые внутренние отступы;
* без вложенных декоративных cards без необходимости.

Плитки добавления и редактирования используют одинаковую структуру labels,
fields, errors и form actions.

На desktop-странице оборудования плитка добавления расположена слева в
фиксированной колонке `280px`, а список занимает оставшуюся ширину. Заголовок
страницы показывает общее количество позиций. Действующее оборудование
находится в основной плитке, а списанное — в отдельной плитке ниже со своим
счётчиком. Форма и списки остаются отдельными surfaces без вложенных
декоративных cards.

На desktop-странице редактирования опасная операция списания располагается
отдельной плиткой справа от плитки состояния, чтобы оставаться доступной без
прокрутки. Она не объединяется с обычными полями, визуально обозначается как
необратимое действие и ведёт на отдельную страницу подтверждения. При
недостаточной ширине плитка списания переносится ниже плитки состояния.

## Buttons и ссылки

Иерархия действий:

* основное действие страницы — filled primary;
* вторичное — tonal или outline;
* навигационное — ссылка или tonal button;
* опасное — danger.

В таблице:

* «Редактировать» — компактная синяя outline button, которая получает primary
  заливку при hover и keyboard focus;
* «Списать» — компактная danger outline button у доступного оборудования и
  оборудования на обслуживании;
* «Удалить» — компактная danger outline button у списанного оборудования;
* filled danger используется только на финальной странице подтверждения.

Опасные действия отделяются от обычных действий пространственно и текстовым
предупреждением. Необратимое списание и удаление требуют отдельного
подтверждения без JavaScript dialog.

Buttons имеют понятный текст. Icon-only действие допускается только при
общеизвестном значении и обязательном `aria-label`.

Высота обычной button и form control — `40px`. Компактные действия в desktop-
таблице имеют высоту `32px`, но сохраняют удобный focus и достаточное расстояние
между соседними опасными действиями.

## Forms

Каждое поле имеет:

* видимый `label`;
* связанный `for`/`id`;
* понятное текущее значение;
* ошибку рядом с полем;
* `aria-invalid` и `aria-describedby` при ошибке.

Placeholder не заменяет label. Основное submit-действие визуально отделено от
cancel и danger actions. Порядок Tab соответствует визуальному порядку.

## Tables, statuses и feedback

Таблица использует:

* нейтральный header;
* компактные строки;
* читаемые заголовки столбцов;
* hover без сдвига layout;
* отдельную компактную колонку действий;
* ссылку на карточку в основном идентификаторе записи.

Status chip содержит точный текст. Цвет только усиливает, но не заменяет
состояние.

Результат операции показывается единым alert-компонентом. Сообщение называет
объект, например:

```text
Оборудование Весло STATUS-CHECK-001 обновлено.
```

Success, warning и error alerts используют `role="status"` или `role="alert"`
в соответствии с назначением и не раскрывают внутренние ошибки.

## Accessibility и движение

Обязательны:

* достаточный контраст текста и controls;
* видимый `:focus-visible`;
* полная keyboard navigation;
* семантические landmarks и headings;
* доступные labels;
* текстовое описание статусов;
* отсутствие зависимости от hover;
* `prefers-reduced-motion`.

Переходы состояния допускаются в пределах `150–200ms` и не должны менять
геометрию соседних элементов.

## Использование UI/UX skill

При доступности `ui-ux-pro-max` используется для проверки структуры,
понятности, контраста, accessibility и UI-антипаттернов.

Рекомендация skill не применяется автоматически, если она:

* меняет утверждённый visual direction;
* требует внешней зависимости;
* вводит SPA, Tailwind, внешний font или animation library;
* делает tablet/mobile обязательной частью текущего инкремента.

Обнаруженное улучшение, выходящее за текущий инкремент, сначала предлагается
отдельно.

## Браузерная приёмка

Каждый UI-инкремент проверяется пользователем на целевом desktop viewport.
Сценарий должен подтвердить:

* единый shell и style;
* понятность основного действия;
* корректные success/error messages;
* Tab-навигацию и focus;
* отсутствие утечки внутренних ошибок;
* сохранение фактического бизнес-поведения.

Tablet/mobile не включаются в текущую приёмку без отдельного согласования.
