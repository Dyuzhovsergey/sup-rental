# SUP Rental

SUP Rental — учебное приложение для учёта оборудования и аренды SUP-досок.

Проект разрабатывается для практического изучения Go и настройки совместной работы с Codex в VS Code.

## Статус проекта

Этап технического вертикального среза и этап учёта оборудования завершены.
Начат этап аутентификации, ролей и аудита: добавлены доменная модель
пользователя, правила login и password, Argon2id password hasher и PostgreSQL
repository пользователей. Административный CLI создаёт единственного `admin`
и безопасно заменяет его password с обязательным audit event. Добавлены
PostgreSQL server-side sessions с отзывом всех сессий admin при замене password.

В проекте уже есть HTTP-сервер, PostgreSQL, миграции, Docker Compose и первый
бизнес-срез учёта оборудования:

```text
GET /
GET /health
GET /equipment
POST /equipment
GET /equipment/{id}
GET /equipment/{id}/retire
POST /equipment/{id}/retire
GET /equipment/{id}/delete
POST /equipment/{id}/delete
GET /equipment/{id}/edit
POST /equipment/{id}/edit
```

Приложение можно запустить вместе с PostgreSQL через Docker Compose. Миграции
применяются до запуска HTTP-сервера.

Хранение пользователей, создание admin и внутренний слой сессий реализованы.
Login, session cookie и защита пользовательских маршрутов пока не реализованы.
Текущая сборка является локальной development-версией: не публикуйте её в
локальную сеть или интернет. В частности, существующие страницы оборудования
пока открываются без login.

Текущий Compose публикует application port на всех host-интерфейсах, а пример
`HTTP_ADDRESS=:8080` также не ограничивает direct-запуск loopback-интерфейсом.
Поэтому требование «только один компьютер» пока организационное, а не
технически enforced: запускайте сборку только на доверенном компьютере в
защищённой локальной среде. Loopback binding будет обязательной частью этапа
доступа до эксплуатационной приёмки.

`GET /` пока показывает техническую HTML-страницу. После реализации доступа
корневой маршрут будет перенаправлять неавторизованного пользователя на login,
а вошедшего пользователя — в интерфейс его роли. `GET /health` останется
отдельным публичным техническим endpoint.

## Подтверждённые требования

На текущем этапе определено следующее:

* существуют две функциональные роли: `admin` и `operator`;
* в системе существует ровно один неизменяемый `admin`;
* администратор управляет оборудованием и учётными записями операторов;
* оператор работает с клиентами и арендой и не изменяет инвентарь;
* пользовательский интерфейс доступен только после будущей аутентификации;
* права на защищённые действия проверяются сервером;
* критические действия сохраняются в audit log с идентификатором исполнителя;
* учитываются SUP-доски, вёсла и спасательные жилеты;
* каждый предмет имеет уникальный инвентарный номер;
* весь физический инвентарь представлен одной сущностью;
* состояния оборудования: доступен, выдан, на обслуживании и списан;
* бронирование будет отдельной будущей сущностью;
* для клиента хранятся ФИО и номер телефона;
* история аренд должна сохраняться;
* аренда является почасовой;
* одна аренда может включать несколько SUP-досок, вёсел и спасательных жилетов;
* скидки не используются;
* доступ к приложению через интернет не требуется.

## Техническое направление

Планируемый технический стек:

* Go;
* PostgreSQL;
* `tern` для миграций PostgreSQL;
* стандартный пакет `log/slog`;
* серверный HTML через `html/template`;
* общий встроенный CSS в стиле Modern SaaS Admin Dashboard;
* Docker;
* Docker Compose.

Для безопасного хранения будущих password hashes используется официальный
Go-модуль `golang.org/x/crypto/argon2`. Открытые пароли приложение хранить не
будет.

Приложение будет разрабатываться как модульный монолит с явной передачей зависимостей через конструкторы.

Интерфейс остаётся server-rendered, с системным шрифтом и минимальным
JavaScript. Целевые размеры текущей браузерной приёмки — `1366×768` и
`1440×900`; специальная адаптация под планшет и телефон пока отложена.
Техническое состояние приложения не будет отображаться на пользовательских
панелях.

На начальном этапе не планируется использовать микросервисы, Kubernetes,
брокеры сообщений и отдельное SPA-приложение.

## Рекомендуемый локальный запуск

Для основного запуска требуются:

* Git;
* Docker с командой `docker compose`.

Локально устанавливать Go, PostgreSQL и `tern` для этого способа не нужно.

### Первый запуск из Git

Выполните одну последовательность команд:

```bash
git clone https://github.com/Dyuzhovsergey/sup-rental.git
cd sup-rental
cp .env.example .env
docker compose config --quiet
docker compose up --build -d
docker compose ps -a
```

Compose автоматически создаст внутреннюю сеть и named volume PostgreSQL,
дождётся готовности базы, применит миграции и только после этого запустит
приложение.

Ожидаемое состояние сервисов:

* `postgres` — `healthy`;
* `migrate` — `Exited (0)`;
* `app` — `healthy`.

Если порт `8080` занят, измените в `.env`:

```dotenv
COMPOSE_HTTP_PORT=18080
```

### Проверка результата

Откройте в браузере на локальном компьютере. Для UI-приёмки используйте viewport
`1366×768` или `1440×900`:

```text
http://localhost:8080/equipment
```

Инвентарный номер в таблице является ссылкой на отдельную карточку предмета.
Карточка показывает номер, тип, состояние и внутренний ID. Для доступного
оборудования и оборудования на обслуживании из карточки можно перейти к
редактированию. На desktop-странице форма добавления расположена слева, а
списки с фактическими количествами позиций — справа. Общий счётчик находится в
заголовке страницы. Действующее оборудование показано в основной плитке, а
списанное — в отдельной плитке ниже. В списке у редактируемых предметов
отображается синяя outline-кнопка «Редактировать», которая получает синюю
заливку при hover и keyboard focus. Для доступного оборудования и оборудования
на обслуживании рядом находится красная outline-кнопка «Списать», ведущая на
отдельную страницу подтверждения. У списанного оборудования отображается
кнопка «Удалить». Две кнопки действий располагаются в одной строке.

Все бизнес-страницы оборудования используют общий интерфейс Modern SaaS Admin
Dashboard: sidebar, единые panels, forms, status chips, alerts и компактные
действия таблицы. Стили встроены в Go-бинарник и не требуют внешних шрифтов,
CSS-фреймворков или JavaScript.

Или выполните:

```bash
curl -i http://localhost:8080/health
curl -i http://localhost:8080/equipment
docker compose logs migrate
docker compose exec postgres \
    psql -U sup_rental -d sup_rental \
    -c "SELECT version FROM public.schema_version;"
```

Все GET-запросы должны вернуть `200 OK`, а версия миграции должна быть `4`.

Эти ответы подтверждают текущее незащищённое development-поведение. Они не
означают, что аутентификация и разграничение прав уже работают.

Оборудование можно добавить через HTML-форму или командой:

```bash
curl -i -X POST \
    --data-urlencode "inventory_number=SUP-001" \
    --data-urlencode "kind=sup_board" \
    http://localhost:8080/equipment
```

Успешный запрос возвращает `303 See Other` с переходом на `/equipment`.
После создания откройте карточку по ссылке в таблице или выполните команду,
заменив `1` на существующий ID:

```bash
curl -i http://localhost:8080/equipment/1
```

Для доступного оборудования и оборудования на обслуживании ссылка
«Редактировать» доступна в карточке выбранного предмета. На отдельной странице
можно исправить инвентарный номер и тип, а также переключить статус между
«Доступен» и «На обслуживании». Выданные и списанные предметы не редактируются.

Изменение также можно проверить через `curl`, заменив `1` на ID из таблицы:

```bash
curl -i -X POST \
    --data-urlencode "inventory_number=SUP-001-UPDATED" \
    --data-urlencode "kind=life_jacket" \
    --data-urlencode "status=maintenance" \
    http://localhost:8080/equipment/1/edit
```

Успешный запрос возвращает `303 See Other` с переходом на `/equipment` и
параметрами выполненной операции. Страница списка показывает подтверждение с
фактически сохранёнными типом и номером:

```text
Оборудование <Тип> <Инвентарный номер> обновлено.
```

Инвентарный номер остаётся обязательным и уникальным без учёта регистра.

На странице списка колонка «Статус» только отображает текущее состояние.
Изменение между «Доступен» и «На обслуживании» выполняется вместе с номером и
типом на странице редактирования. Все три значения сохраняются одной операцией.
Статус «Выдан» меняется будущими сценариями выдачи и возврата.

Списание начинается из отдельной опасной плитки под основными данными страницы
редактирования.
Перед необратимым переходом приложение показывает данные предмета,
предупреждение и кнопки подтверждения и отмены. Отмена возвращает к
редактированию без изменения данных. После подтверждения оборудование получает
состояние «Списан», приложение возвращается к списку и показывает сообщение:

```text
Оборудование <Тип> <Инвентарный номер> списано.
```

Списанный предмет больше не редактируется и не меняет состояние. Выбрать
`retired` в обычном поле статуса нельзя.

Списанное оборудование можно безвозвратно удалить из списка или его карточки.
Удаление выполняется только после перехода на отдельную страницу подтверждения.
У доступного оборудования и оборудования на обслуживании вместо удаления
показывается действие «Списать». Прямая попытка удалить несписанный предмет
отклоняется. Когда появятся аренды, оборудование, связанное с их историей,
также не должно удаляться. После успешного удаления список показывает:

```text
Оборудование <Тип> <Инвентарный номер> удалено.
```

Управление оборудованием и общий интерфейс прошли браузерную приёмку.

### Остановка и повторный запуск

Остановите контейнеры:

```bash
docker compose down
```

Обычный `down` сохраняет named volume с данными PostgreSQL. Для повторного
запуска достаточно:

```bash
docker compose up -d
```

Команда `docker compose down -v` удаляет volume вместе с данными и не должна
выполняться без осознанного решения и резервной копии.

PostgreSQL-порт `5432` не публикуется на host. Контейнеры обращаются к базе по
внутреннему hostname `postgres`, поэтому Compose не конфликтует с PostgreSQL,
установленной непосредственно на компьютере.

## Дополнительный запуск без Docker Compose

Этот способ полезен при разработке Go-кода, но требует локально установленных Go,
PostgreSQL и `tern`.

### Конфигурация приложения

Приложение использует обязательные переменные окружения:

* `HTTP_ADDRESS` — адрес в формате `host:port`, например `:8080`;
* `HTTP_READ_HEADER_TIMEOUT` — максимальное время чтения заголовков запроса
  в формате Go `time.Duration`, например `5s`;
* `HTTP_SHUTDOWN_TIMEOUT` — максимальное время ожидания активных запросов
  при корректном завершении сервера, например `10s`;
* `DATABASE_URL` — connection string локальной PostgreSQL;
* `DB_CONNECT_TIMEOUT` — максимальное время подключения к PostgreSQL,
  например `5s`.

Несекретный пример значений находится в `.env.example`.

### Подготовка локальной PostgreSQL

Перед первым запуском создайте пользователя и базу данных. Выполните в `psql`
от имени администратора PostgreSQL:

```sql
CREATE ROLE sup_rental WITH LOGIN PASSWORD 'sup_rental';
CREATE DATABASE sup_rental OWNER sup_rental;
```

Connection string не создаёт пользователя, базу данных или таблицы
автоматически.

### Переменные окружения

Создайте локальный `.env` из примера и загрузите значения в текущий shell:

```bash
cp .env.example .env
set -a
source .env
set +a
go run ./cmd/server
```

`set -a` включает автоматический export переменных, а `set +a` выключает его
после загрузки `.env`. Файл `.env` не сохраняется в Git.

После успешного подключения появляется log `connected to PostgreSQL`.

В браузере откройте пользовательскую страницу оборудования:

```text
http://localhost:8080/equipment
```

В другом терминале страницу и health endpoint можно проверить командами:

```bash
curl -i http://localhost:8080/health
curl -i http://localhost:8080/equipment
```

Все запросы должны вернуть `200 OK`. Тело ответа `/health`:

```text
ok
```

Для корректного завершения сервера нажмите `Ctrl+C`. Сервер прекратит принимать
новые подключения, дождётся активных запросов в пределах
`HTTP_SHUTDOWN_TIMEOUT` и завершится с кодом `0`.

Переменная `TEST_DATABASE_URL` используется integration-тестами подключения и
PostgreSQL repositories оборудования и пользователей. Без неё тесты явно
пропускаются. Перед integration-тестами repositories к тестовой базе необходимо
применить миграции.

### Миграции PostgreSQL

Миграции выполняются отдельно от запуска HTTP-сервера с помощью `tern`.
Это делает изменение схемы явной операцией и не требует добавлять migration tool
в runtime-зависимости приложения.

Установите проверенную для проекта версию `tern`:

```bash
go install github.com/jackc/tern/v2@v2.4.0
```

После загрузки переменных из `.env` примените миграции:

```bash
tern migrate --migrations migrations
```

Текущий статус можно проверить командой:

```bash
tern status --migrations migrations
```

Первая baseline-миграция проверяет механизм миграций. Вторая миграция создаёт
таблицу `equipment`, третья — таблицу `users` с уникальными login и ограничением
на единственную учётную запись `admin`, четвёртая — append-only основу
`audit_events`, пятая — PostgreSQL server-side sessions. `tern` также использует
служебную таблицу `public.schema_version`, в которой хранит номер применённой
миграции.

Откат прикладных миграций удаляет соответствующую таблицу вместе со всеми
внесёнными данными, поэтому не выполняйте его на рабочей базе без осознанного
решения и резервной копии.

### Создание и восстановление admin

Первый `admin` не создаётся миграцией. После применения миграций запустите
интерактивную CLI-команду:

```bash
docker compose run --rm --build admin create
```

CLI запросит неизменяемый login, password и его повтор. Password читается
только из интерактивного terminal без отображения символов и не принимается
через аргументы команды или переменные окружения.

Для безопасной замены забытого password используйте:

```bash
docker compose run --rm admin reset-password
```

Команда сама находит единственного `admin`; login вводить не требуется. Успешное
создание и замена password записываются вместе с изменением в одной
PostgreSQL-транзакции. Замена password также немедленно отзывает все действующие
сессии admin в этой же транзакции.

### Server-side sessions

Таблица `sessions` хранит серверное состояние сессии, привязанное к активному
пользователю. Browser в будущем получит только случайный raw token, а
PostgreSQL хранит его SHA-256 digest. Отдельный session-bound CSRF token
подготовлен для защиты изменяющих HTML-форм.

Сессия имеет idle timeout 8 часов и абсолютный срок 24 часа. Успешная проверка
обновляет `last_seen_at`; истёкшие, отозванные и принадлежащие отключённому
пользователю сессии считаются недействительными. HTTP cookie, login и logout
будут добавлены следующим отдельным инкрементом.

При локальном запуске без Docker после загрузки `.env` доступны те же команды:

```bash
go run ./cmd/admin create
go run ./cmd/admin reset-password
```

Обычный `docker compose up` не запускает CLI: сервис `admin` находится в profile
`tools` и стартует только при явном обращении.

### Docker image

Приложение собирается через multi-stage Dockerfile. Финальный image содержит
скомпилированные server и admin CLI, CA-сертификаты и минимальное runtime-окружение.
Процесс запускается от непривилегированного пользователя `app`.

Соберите image:

```bash
docker build -t sup-rental:dev .
```

Пока PostgreSQL работает непосредственно на Linux host, контейнер можно
запустить через host network:

```bash
docker run --rm \
    --name sup-rental-server \
    --network host \
    --env-file .env \
    sup-rental:dev
```

Такой запуск позволяет использовать текущий `localhost:5432` из
`DATABASE_URL`. После появления Docker Compose приложение будет обращаться к
PostgreSQL по имени сервиса внутри Compose-сети.

Перед запуском освободите порт `8080`, если приложение уже запущено через
`go run`. Для разовой проверки на другом порту можно переопределить только адрес:

```bash
docker run --rm \
    --name sup-rental-server \
    --network host \
    --env-file .env \
    --env HTTP_ADDRESS=127.0.0.1:18080 \
    sup-rental:dev
```

В другом терминале проверьте приложение:

```bash
curl -i http://localhost:8080/health
```

Для остановки нажмите `Ctrl+C`. Docker передаст сигнал приложению, после чего
должен выполниться graceful shutdown.

Проверить, что image запускается не от `root`, можно командой:

```bash
docker run --rm --entrypoint id sup-rental:dev
```

Dockerfile не запускает миграции внутри процесса приложения и не помещает
`.env` в image. При одиночном запуске application image миграции применяются с
host, а при запуске через Docker Compose их выполняет отдельный сервис
`migrate`.
