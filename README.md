# SUP Rental

SUP Rental — учебное приложение для учёта оборудования и аренды SUP-досок.

Проект разрабатывается для практического изучения Go и настройки совместной работы с Codex в VS Code.

## Статус проекта

Этапы технического вертикального среза, учёта оборудования, аутентификации,
ролей и аудита завершены. В рамках этапа доступа добавлены доменная модель
пользователя, правила login и password, Argon2id password hasher и PostgreSQL
repository пользователей. Административный CLI создаёт единственного `admin`
и безопасно заменяет его password с обязательным audit event. Добавлены
PostgreSQL server-side sessions с отзывом всех сессий admin при замене password.
Реализованы login/logout, session cookie, PostgreSQL throttling, CSRF-защита
изменяющих HTML-форм, серверная проверка ролей и обязательные audit events
операций аутентификации.
Администратор может создавать, отключать и активировать операторов и заменять
их постоянные password. Изменения учётных записей и оборудования записываются
в `audit_events` вместе с идентификатором администратора. Реализована
admin-only страница просмотра журнала с безопасными фильтрами.

Начат этап учёта клиентов: добавлены независимая доменная модель клиента,
нормализация российских и явно международных телефонных номеров в канонический
формат E.164, таблица `clients` и PostgreSQL repository. Реализованы защищённая
страница списка, точный поиск по нормализованному телефону и создание клиента
активным оператором с обязательным транзакционным audit. Дополнительно
реализованы карточка клиента и редактирование контактных данных оператором с
атомарным `client.updated`. Интерфейс прошёл браузерную приёмку.

Начат этап аренды: пакет `internal/rental` задаёт независимую доменную модель,
получасовой полуоткрытый интервал, состав из отдельных физических единиц,
снимки тарифов, предварительную стоимость и разрешённые переходы состояний.
Хранение аренд в PostgreSQL и пользовательский интерфейс пока не реализованы.

В проекте уже есть HTTP-сервер, PostgreSQL, миграции, Docker Compose и первый
бизнес-срез учёта оборудования:

```text
GET /
GET /health
GET /login
POST /login
POST /logout
GET /operator
GET /admin/operators
POST /admin/operators
GET /admin/operators/{id}/disable
POST /admin/operators/{id}/disable
POST /admin/operators/{id}/activate
GET /admin/operators/{id}/password
POST /admin/operators/{id}/password
GET /admin/audit
GET /clients
POST /clients
GET /clients/{id}
GET /clients/{id}/edit
POST /clients/{id}/edit
GET /equipment
POST /equipment
GET /equipment/{id}
GET /equipment/{id}/retire
POST /equipment/{id}/retire
GET /equipment/{id}/delete
POST /equipment/{id}/delete
GET /equipment/{id}/edit
POST /equipment/{id}/edit
POST /equipment/{id}/model
POST /equipment/{id}/rate
```

Приложение можно запустить вместе с PostgreSQL через Docker Compose. Миграции
применяются до запуска HTTP-сервера.

Хранение пользователей, создание admin, server-side sessions, login/logout,
защита бизнес-маршрутов и проверка ролей реализованы. Текущая сборка остаётся
локальной development-версией: не публикуйте её в локальную сеть или интернет.

Compose публикует application port только на `127.0.0.1`. Пример direct-запуска
также использует `HTTP_ADDRESS=127.0.0.1:8080`. Не меняйте binding на LAN до
отдельного инкремента с HTTPS и обязательным `Secure` для session cookie.

`GET /` перенаправляет неавторизованного пользователя на login, `admin` — на
`/equipment`, а `operator` — на `/operator`. `GET /health` остаётся отдельным
публичным техническим endpoint.

## Подтверждённые требования

На текущем этапе определено следующее:

* существуют две функциональные роли: `admin` и `operator`;
* в системе существует ровно один неизменяемый `admin`;
* администратор управляет оборудованием и учётными записями операторов;
* оператор работает с клиентами и арендой и не изменяет инвентарь;
* пользовательский интерфейс доступен только после аутентификации;
* права на защищённые действия проверяются сервером;
* критические действия сохраняются в audit log с идентификатором исполнителя;
* учитываются SUP-доски, вёсла и спасательные жилеты;
* каждый предмет получает уникальный номер вида `PREFIX-MODEL-SEQUENCE`;
* модель объединяет тип, латинский код и общий часовой тариф;
* весь физический инвентарь представлен одной сущностью;
* состояния оборудования: доступен, выдан, на обслуживании и списан;
* бронирование будет отдельной будущей сущностью;
* для клиента хранятся ФИО и номер телефона;
* история аренд должна сохраняться;
* аренда является почасовой;
* одна аренда может включать несколько SUP-досок, вёсел и спасательных жилетов;
* скидки не используются;
* доступ к приложению через интернет не требуется.

Подробные подтверждённые требования описаны в:

  клиенты и аренды;

### Доменная модель клиента

Пакет `internal/client` хранит ФИО одной нормализованной строкой и телефон
отдельным типом `Phone`. Внешние пробелы ФИО удаляются, внутренние пробельные
последовательности заменяются одним пробелом. Управляющие символы, пустое ФИО и
значение длиннее 200 Unicode-символов отклоняются.

Телефон хранится как `+` и цифры без разделителей. Номер из 10 цифр считается
российским; префиксы `8` и `7` в российских 11-значных формах приводятся к
`+7`. Явно международный номер должен начинаться с `+`. Нормализация проверяет
формат и длину, но не существование номера и не принадлежность абоненту.

### Доменная модель аренды

Пакет `internal/rental` создаёт аренду для существующего клиента в состоянии
`draft`. Планируемый интервал задаётся границами, кратными 30 минутам, и длится
не менее одного получасового слота. Интервал полуоткрытый: момент начала входит
в аренду, а момент окончания — нет. Поэтому аренда `10:00–11:00` не
пересекается с арендой `11:00–12:00`.

Жизненный цикл ограничен переходами `draft → confirmed/cancelled`,
`confirmed → active/cancelled` и `active → completed`. Состояния `completed` и
`cancelled` являются конечными. Пустой черновик можно отменить, но нельзя
подтвердить.

Состав хранит отдельный снимок каждой физической единицы: ID, инвентарный
номер, тип, модель и часовой тариф. Его можно менять только в `draft`, а
повторное добавление одного Equipment ID отклоняется. Предварительная стоимость
суммирует тарифы всех позиций и умножает половину часовой суммы на число
30-минутных слотов. Расчёт выполняется в копейках через `int64`, без `float` и
округления. PostgreSQL и пользовательский интерфейс аренды будут добавлены
отдельными инкрементами.

## Техническое направление

Планируемый технический стек:

* Go;
* PostgreSQL;
* `tern` для миграций PostgreSQL;
* стандартный пакет `log/slog`;
* серверный HTML через `html/template`;
* общий встроенный CSS в стиле Modern SaaS Admin Dashboard;
* Docker;
* Docker Compose.

Для безопасного хранения будущих password hashes используется официальный
Go-модуль `golang.org/x/crypto/argon2`. Открытые пароли приложение хранить не
будет.

Приложение будет разрабатываться как модульный монолит с явной передачей зависимостей через конструкторы.

Интерфейс остаётся server-rendered, с системным шрифтом и минимальным
JavaScript. Целевые размеры текущей браузерной приёмки — `1366×768` и
`1440×900`; специальная адаптация под планшет и телефон пока отложена.
Техническое состояние приложения не будет отображаться на пользовательских
панелях.

На начальном этапе не планируется использовать микросервисы, Kubernetes,
брокеры сообщений и отдельное SPA-приложение.

## Принципы разработки

Разработка ведётся небольшими, законченными и проверяемыми инкрементами.

Каждое существенное архитектурное решение должно быть объяснено. Новые библиотеки и инфраструктурные компоненты добавляются только при наличии конкретной необходимости.

## Рекомендуемый локальный запуск

Для основного запуска требуются:

* Git;
* Docker с командой `docker compose`.

Локально устанавливать Go, PostgreSQL и `tern` для этого способа не нужно.

### Первый запуск из Git

Выполните одну последовательность команд:

```bash
git clone https://github.com/Dyuzhovsergey/sup-rental.git
cd sup-rental
cp .env.example .env
docker compose config --quiet
docker compose up --build -d
docker compose ps -a
docker compose run --rm admin create
```

Compose автоматически создаст внутреннюю сеть и named volume PostgreSQL,
дождётся готовности базы, применит миграции и только после этого запустит
приложение.

Ожидаемое состояние сервисов:

* `postgres` — `healthy`;
* `migrate` — `Exited (0)`;
* `app` — `healthy`.

Если порт `8080` занят, измените в `.env`:

```dotenv
COMPOSE_HTTP_PORT=18080
```

### Проверка результата

Откройте в браузере на локальном компьютере. Для UI-приёмки используйте viewport
`1366×768` или `1440×900`:

```text
http://localhost:8080/login
```

Войдите с login и password единственного `admin`, созданного CLI-командой.
После успешного входа откроется `/equipment`. Неавторизованный переход на
`/equipment` автоматически возвращает пользователя на `/login`.

Инвентарный номер в таблице является ссылкой на отдельную карточку предмета.
Карточка показывает номер, тип, модель, часовой тариф, состояние и внутренний ID. Для доступного
оборудования и оборудования на обслуживании из карточки можно перейти к
редактированию. На desktop-странице форма добавления расположена слева, а
списки с фактическими количествами позиций — справа. Общий счётчик находится в
заголовке страницы. Действующее оборудование показано в основной плитке, а
списанное — в отдельной плитке ниже. В списке у редактируемых предметов
отображается синяя outline-кнопка «Редактировать», которая получает синюю
заливку при hover и keyboard focus. Для доступного оборудования и оборудования
на обслуживании рядом находится оранжевая outline-кнопка «Списать», ведущая на
отдельную страницу подтверждения. У списанного оборудования отображается
кнопка «Удалить». Две кнопки действий располагаются в одной строке.

Обе таблицы оборудования имеют независимую пагинацию. Общий переключатель
задаёт по 5, 10 или 15 строк для каждой таблицы; по умолчанию отображается 5.
Переход по страницам действующего оборудования сохраняет текущую страницу
списанного оборудования и наоборот.

Все бизнес-страницы оборудования используют общий интерфейс Modern SaaS Admin
Dashboard: sidebar, единые panels, forms, status chips, alerts и компактные
действия таблицы. Стили встроены в Go-бинарник и не требуют внешних шрифтов,
CSS-фреймворков или JavaScript.

Роль `operator` после входа попадает на `/operator` и может открывать список и
карточки оборудования только для просмотра. Формы добавления, редактирования,
списания и удаления не отображаются, а прямые запросы к административным
маршрутам отклоняются сервером с `403 Forbidden`.

Обе роли могут открыть `/clients`, просматривать постраничный список и искать
клиента по телефону. Введённый номер нормализуется перед точным поиском.
Только активный `operator` видит форму и может создать клиента; прямой POST от
`admin` отклоняется сервером. Успешное создание и `client.created` записываются
одной PostgreSQL-транзакцией, при этом телефон и содержимое формы в audit log
не сохраняются. ФИО в списке ведёт на карточку, доступную обеим ролям. Только
активный `operator` может открыть форму редактирования и изменить ФИО или
телефон; `admin` сохраняет read-only доступ, защищённый также серверной
проверкой маршрута. Обновление и `client.updated` записываются одной
PostgreSQL-транзакцией. Audit хранит изменения ФИО и только признак изменения
телефона, но не сам номер. В `/admin/audit` доступен фильтр категории
«Клиенты». После успешного редактирования оператор возвращается к списку с
сообщением об обновлении. Список показывает по 5 клиентов по умолчанию;
доступны варианты 5, 10 и 15 строк с сохранением выбора в пагинации. ФИО
остаётся ссылкой на карточку, но отображается без постоянного подчёркивания.

Или выполните:

```bash
curl -i http://localhost:8080/health
curl -i http://localhost:8080/equipment
docker compose logs migrate
docker compose exec postgres \
    psql -U sup_rental -d sup_rental \
    -c "SELECT version FROM public.schema_version;"
```

`/health` должен вернуть `200 OK`, а неавторизованный `/equipment` —
`302 Found` с `Location: /login`. Версия миграции должна быть `8`.

Изменяющие формы требуют session cookie и session-bound CSRF token, поэтому
проверяйте бизнес-операции через browser. Не копируйте session или CSRF token в
shell-команды и logs.

Форма добавления создаёт партию отдельных физических единиц. Администратор
выбирает тип, вводит латинский код модели, положительный целый тариф в рублях
за час и количество от 1 до 100. Номер вводить не нужно. Например, три весла
модели `CARBON` получат `PADDLE-CARBON-1` — `PADDLE-CARBON-3`. Повторная партия
с тем же тарифом продолжает нумерацию; другой тариф той же модели возвращает
понятный конфликт без создания записей.
Недавно добавленные единицы отображаются в начале списка оборудования.

Для доступного оборудования и оборудования на обслуживании ссылка
«Редактировать» доступна в карточке выбранного предмета. Страница позволяет:

* переключить статус между «Доступен» и «На обслуживании»;
* перенести физическую единицу в существующую или новую модель;
* изменить общий часовой тариф текущей модели.

При переносе формируется следующий номер целевой модели; внутренний ID и статус
сохраняются. Для существующей модели введённый тариф должен совпадать с её
текущим тарифом. Тариф изменяется отдельной формой и сразу применяется ко всем
единицам модели. Выданные и списанные предметы не редактируются.

Успешный запрос возвращает `303 See Other` с переходом на `/equipment` и
параметрами выполненной операции. Страница списка показывает подтверждение с
фактически сохранёнными типом и номером:

```text
Оборудование <Тип> <Инвентарный номер> обновлено.
```

Инвентарный номер вычисляется автоматически и не редактируется вручную.

На странице списка колонка «Статус» только отображает текущее состояние.
Изменение между «Доступен» и «На обслуживании» выполняется на странице
редактирования. Перенос предмета и изменение общего тарифа находятся в
отдельных плитках с предупреждением об области действия.
На desktop плитка списания расположена справа от плитки состояния и ведёт на
отдельную страницу подтверждения.
Статус «Выдан» меняется будущими сценариями выдачи и возврата.

Списание начинается из отдельной опасной плитки справа от состояния на
desktop-странице редактирования.
Перед необратимым переходом приложение показывает данные предмета,
предупреждение и кнопки подтверждения и отмены. Отмена возвращает к
редактированию без изменения данных. После подтверждения оборудование получает
состояние «Списан», приложение возвращается к списку и показывает сообщение:

```text
Оборудование <Тип> <Инвентарный номер> списано.
```

Списанный предмет больше не редактируется и не меняет состояние. Выбрать
`retired` в обычном поле статуса нельзя.

Списанное оборудование можно безвозвратно удалить из списка или его карточки.
Удаление выполняется только после перехода на отдельную страницу подтверждения.
У доступного оборудования и оборудования на обслуживании вместо удаления
показывается действие «Списать». Прямая попытка удалить несписанный предмет
отклоняется. Когда появятся аренды, оборудование, связанное с их историей,
также не должно удаляться. После успешного удаления список показывает:

```text
Оборудование <Тип> <Инвентарный номер> удалено.
```

Управление оборудованием и общий интерфейс прошли браузерную приёмку.

Каждая партия создаёт одно `equipment.batch_created` с типом, моделью, тарифом,
количеством и диапазоном номеров. Перенос единицы записывает
`equipment.model_changed` со старым и новым номером, а общий тариф —
`equipment.model_rate_changed` со старым и новым значением и количеством
затронутых единиц. Изменение состояния, списание и удаление также записываются
в `audit_events` вместе с ID, login и ролью администратора.
Бизнес-изменение и audit event выполняются одной PostgreSQL-транзакцией; ошибка
аудита откатывает всю операцию.

Администратору доступен read-only журнал по адресу `/admin/audit`. События
отображаются от новых к старым с московским временем и страницами по 50 строк.
Фильтры позволяют выбрать категорию, результат, исполнителя, объект и период.
Интерфейс показывает только заранее разрешённые безопасные поля из `details`;
неизвестные структурированные данные целиком не выводятся. Оператор получает
`403 Forbidden` при прямом обращении к журналу.

### Остановка и повторный запуск

Остановите контейнеры:

```bash
docker compose down
```

Обычный `down` сохраняет named volume с данными PostgreSQL. Для повторного
запуска достаточно:

```bash
docker compose up -d
```

Команда `docker compose down -v` удаляет volume вместе с данными и не должна
выполняться без осознанного решения и резервной копии.

PostgreSQL-порт `5432` не публикуется на host. Контейнеры обращаются к базе по
внутреннему hostname `postgres`, поэтому Compose не конфликтует с PostgreSQL,
установленной непосредственно на компьютере.

## Дополнительный запуск без Docker Compose

Этот способ полезен при разработке Go-кода, но требует локально установленных Go,
PostgreSQL и `tern`.

### Конфигурация приложения

Приложение использует обязательные переменные окружения:

* `HTTP_ADDRESS` — адрес в формате `host:port`, для локального запуска
  `127.0.0.1:8080`;
* `HTTP_READ_HEADER_TIMEOUT` — максимальное время чтения заголовков запроса
  в формате Go `time.Duration`, например `5s`;
* `HTTP_SHUTDOWN_TIMEOUT` — максимальное время ожидания активных запросов
  при корректном завершении сервера, например `10s`;
* `DATABASE_URL` — connection string локальной PostgreSQL;
* `DB_CONNECT_TIMEOUT` — максимальное время подключения к PostgreSQL,
  например `5s`.
* `SESSION_COOKIE_SECURE` — `false` только для согласованного loopback HTTP;
  при HTTPS обязательно `true`.

Несекретный пример значений находится в `.env.example`.

### Подготовка локальной PostgreSQL

Перед первым запуском создайте пользователя и базу данных. Выполните в `psql`
от имени администратора PostgreSQL:

```sql
CREATE ROLE sup_rental WITH LOGIN PASSWORD 'sup_rental';
CREATE DATABASE sup_rental OWNER sup_rental;
```

Connection string не создаёт пользователя, базу данных или таблицы
автоматически.

### Переменные окружения

Создайте локальный `.env` из примера и загрузите значения в текущий shell:

```bash
cp .env.example .env
set -a
source .env
set +a
go run ./cmd/server
```

`set -a` включает автоматический export переменных, а `set +a` выключает его
после загрузки `.env`. Файл `.env` не сохраняется в Git.

После успешного подключения появляется log `connected to PostgreSQL`.

В браузере откройте страницу входа:

```text
http://localhost:8080/login
```

В другом терминале страницу и health endpoint можно проверить командами:

```bash
curl -i http://localhost:8080/health
curl -i http://localhost:8080/login
```

Оба публичных запроса должны вернуть `200 OK`. Тело ответа `/health`:

```text
ok
```

Для корректного завершения сервера нажмите `Ctrl+C`. Сервер прекратит принимать
новые подключения, дождётся активных запросов в пределах
`HTTP_SHUTDOWN_TIMEOUT` и завершится с кодом `0`.

Переменная `TEST_DATABASE_URL` используется integration-тестами подключения и
PostgreSQL repositories оборудования, пользователей и клиентов. Без неё тесты явно
пропускаются. Перед integration-тестами repositories к тестовой базе необходимо
применить миграции.

### Миграции PostgreSQL

Миграции выполняются отдельно от запуска HTTP-сервера с помощью `tern`.
Это делает изменение схемы явной операцией и не требует добавлять migration tool
в runtime-зависимости приложения.

Установите проверенную для проекта версию `tern`:

```bash
go install github.com/jackc/tern/v2@v2.4.0
```

После загрузки переменных из `.env` примените миграции:

```bash
tern migrate --migrations migrations
```

Текущий статус можно проверить командой:

```bash
tern status --migrations migrations
```

Первая baseline-миграция проверяет механизм миграций. Вторая миграция создаёт
таблицу `equipment`, третья — таблицу `users` с уникальными login и ограничением
на единственную учётную запись `admin`, четвёртая — append-only основу
`audit_events`, пятая — PostgreSQL server-side sessions, шестая — постоянные
счётчики login throttling, седьмая — таблицу `clients` с уникальным
нормализованным телефоном. `tern` также использует служебную таблицу
`public.schema_version`, в которой хранит номер применённой миграции.

Таблица `clients` хранит минимальные поля `full_name` и `phone`. PostgreSQL
дополнительно проверяет длину и отсутствие внешних пробелов ФИО, канонический
формат телефона и его уникальность. `ClientRepository` создаёт и атомарно
обновляет клиента, получает его по ID, выводит страницы списка и ищет по
точному нормализованному телефону. Операции подключены к защищённым страницам
`/clients` и `/clients/{id}`; создание и редактирование доступны только
активному оператору.

Откат прикладных миграций удаляет соответствующую таблицу вместе со всеми
внесёнными данными, поэтому не выполняйте его на рабочей базе без осознанного
решения и резервной копии.

### Создание и восстановление admin

Первый `admin` не создаётся миграцией. После применения миграций запустите
интерактивную CLI-команду:

```bash
docker compose run --rm --build admin create
```

CLI запросит неизменяемый login, password и его повтор. Password читается
только из интерактивного terminal без отображения символов и не принимается
через аргументы команды или переменные окружения.

Для безопасной замены забытого password используйте:

```bash
docker compose run --rm admin reset-password
```

Команда сама находит единственного `admin`; login вводить не требуется. Успешное
создание и замена password записываются вместе с изменением в одной
PostgreSQL-транзакции. Замена password также немедленно отзывает все действующие
сессии admin в этой же транзакции.

### Server-side sessions

Таблица `sessions` хранит серверное состояние сессии, привязанное к активному
пользователю. Browser получает только случайный raw token в `HttpOnly`,
`SameSite=Strict` cookie, а PostgreSQL хранит его SHA-256 digest. Отдельный
session-bound CSRF token защищает logout и каждую изменяющую форму оборудования.
Все пользовательские маршруты проверяют сессию и роль на сервере.

Сессия имеет idle timeout 8 часов и абсолютный срок 24 часа. Успешная проверка
обновляет `last_seen_at`; истёкшие, отозванные и принадлежащие отключённому
пользователю сессии считаются недействительными. Вход доступен на `/login`, а
logout отзывает текущую сессию и удаляет cookie.

### Управление операторами

Администратору доступна страница `/admin/operators`. На ней можно создать
учётную запись `operator` с постоянными login и password, посмотреть состояние
и время последнего успешного входа в московском часовом поясе (`МСК`, UTC+3),
отключить или повторно активировать
оператора и задать ему новый password.

Операторы не удаляются физически. Отключение немедленно завершает все активные
сессии, но сохраняет учётную запись и историю. Повторная активация сохраняет
существующий password. Смена password разрешена и для отключённой записи и
также завершает все её активные сессии.

Маршруты управления доступны только роли `admin`, проверяют session-bound CSRF
token для каждого изменения и не показывают password или password hash. Создание,
отключение, активация и смена password атомарно записываются в `audit_events`
вместе с идентификатором администратора.

Неудачные попытки ограничиваются по нормализованному login и IP: 5 и 20 ошибок
за 15 минут соответственно приводят к блокировке на 15 минут. Счётчики хранятся
в PostgreSQL. Для неизвестного пользователя, неправильного password и
отключённой записи интерфейс показывает одинаковое сообщение.

При локальном запуске без Docker после загрузки `.env` доступны те же команды:

```bash
go run ./cmd/admin create
go run ./cmd/admin reset-password
```

Обычный `docker compose up` не запускает CLI: сервис `admin` находится в profile
`tools` и стартует только при явном обращении.

### Docker image

Приложение собирается через multi-stage Dockerfile. Финальный image содержит
скомпилированные server и admin CLI, CA-сертификаты и минимальное runtime-окружение.
Процесс запускается от непривилегированного пользователя `app`.

Соберите image:

```bash
docker build -t sup-rental:dev .
```

Пока PostgreSQL работает непосредственно на Linux host, контейнер можно
запустить через host network:

```bash
docker run --rm \
    --name sup-rental-server \
    --network host \
    --env-file .env \
    sup-rental:dev
```

Такой запуск позволяет использовать текущий `localhost:5432` из
`DATABASE_URL`. После появления Docker Compose приложение будет обращаться к
PostgreSQL по имени сервиса внутри Compose-сети.

Перед запуском освободите порт `8080`, если приложение уже запущено через
`go run`. Для разовой проверки на другом порту можно переопределить только адрес:

```bash
docker run --rm \
    --name sup-rental-server \
    --network host \
    --env-file .env \
    --env HTTP_ADDRESS=127.0.0.1:18080 \
    sup-rental:dev
```

В другом терминале проверьте приложение:

```bash
curl -i http://localhost:8080/health
```

Для остановки нажмите `Ctrl+C`. Docker передаст сигнал приложению, после чего
должен выполниться graceful shutdown.

Проверить, что image запускается не от `root`, можно командой:

```bash
docker run --rm --entrypoint id sup-rental:dev
```

Dockerfile не запускает миграции внутри процесса приложения и не помещает
`.env` в image. При одиночном запуске application image миграции применяются с
host, а при запуске через Docker Compose их выполняет отдельный сервис
`migrate`.
